# Music sync (rclone) and MPD configuration

How the music library gets from Google Drive onto disk and into MPD, which files
are generated vs. version-controlled, and how to change any of it safely.

Read when touching a music sync profile, changing where the library lives,
regenerating `mpd.conf`, or debugging a sync that ran but changed nothing.

> **Tracks and playlists arrive by different mechanisms.** Audio is synced from
> Google Drive by rclone on a timer. Playlists and lyrics are **git**, in the
> `music-metadata` repo, pulled by hand. Nothing automates the second one, and
> nothing should be added to `$SERVICES_PATH` to try: the SSH key is
> passphrase-protected, so a systemd `git pull` has no way to authenticate and
> would fail on every firing.

---

## 1. The four layers — tracks only

| layer | lives at | owned by |
|---|---|---|
| **Backends** | `~/.config/rclone/rclone.conf` | assembled by `rclc` from GPG-encrypted fragments in the `_secured` submodule — never edited directly |
| **Profiles** | `~/.config/rclone-sync-profiles/<name>.conf` | dotfiles (stowed) |
| **Engine** | `/usr/local/bin/rclone-sync.sh` | `$SERVICES_PATH/rclone-sync.sh`, installed via `asm` → 55 — see `service-installation.md` |
| **Scheduler** | `rclone-sync@<profile>.timer` in `/etc/systemd/system` | generated by `install.py` from the profile's `SCHEDULE` — see §4 |

Playlists have none of this. They are a `git clone` of
`github.com:susamn/music-metadata` — by convention at `~/Music/music-metadata`,
but the path is yours to choose and `mpdc configure` asks for it. `playlists/`
inside that clone is what MPD reads; `lyrics/` is what the `fetch_lrc.py` /
`fetch_elrc.py` scripts write into.

A profile is the unit of configuration. `rclone-sync.sh <profile-name>` reads
`~/.config/rclone-sync-profiles/<name>.conf` and does the whole job:

```sh
REMOTE="gdrive"                 # backend name from rclone.conf
REMOTE_PATH="Media/Music"       # path within the backend
LOCAL_PATH="/home/susamn/Music/susamn-music-collection"
SYNC_TYPE="one"                 # one → rclone sync · bidirectional → rclone bisync
DIRECTION="remote-to-local"     # only meaningful when SYNC_TYPE=one
SCHEDULE="*:0/30"               # consumed by install.py to write the timer drop-in
RCLONE_OPTS="--exclude=*.m3u"
```

`REMOTE`, `LOCAL_PATH`, and `SYNC_TYPE` are required; the engine exits if any is
missing. `SYNC_TYPE="one"` means **`rclone sync`, which deletes at the
destination** to make it match the source — with `remote-to-local` the local
directory is disposable and the remote wins.

## 2. `mpd.conf` is generated — do not edit it

This is the same trap as `~/.claude/CLAUDE.md`: the file you would naturally edit
is a build artifact that gets overwritten.

```
dotfiles/.config/mpd/mpd.conf.bak   ← TEMPLATE. version-controlled, stowed. Edit THIS.
            │
            │  mpdc configure   (workspace/scripts/mpd-configurer.sh)
            │  patches only music_directory + playlist_directory
            ▼
~/.config/mpd/mpd.conf              ← GENERATED. real file, not stowed, not tracked.
```

`mpdc configure` asks for two things and rewrites exactly two lines:

| line | comes from |
|---|---|
| `music_directory` | a **tracks** rclone profile, picked by fzf (or typed) — its `LOCAL_PATH` |
| `playlist_directory` | a **path you type**, defaulting to whatever `mpd.conf` already holds, else `~/Music/music-metadata/playlists` |

Everything else in `mpd.conf.bak` is passed through untouched.

The template ships `playlist_directory "@PLAYLIST_DIR@"` — a **placeholder, not a
path**. There is no profile and no repo-side default that could know where you
cloned `music-metadata`, so a plausible-looking real path would just be a wrong
answer applied silently whenever configure had not been run. The placeholder
makes that state fail loudly at MPD startup instead. An invariant test pins it.

Two asymmetries in what gets created, both deliberate:

- `music_directory` **is** created (`mkdir -p`) — it is the destination of an
  rclone sync that owns it outright.
- `playlist_directory` is **never** created, and configure aborts if it does not
  exist. It is a git clone; a mistyped path created on demand would be an empty
  directory that MPD reports as zero playlists, with nothing anywhere saying why.

**Consequence:** the tracks profile's `LOCAL_PATH` is the single source of truth
for where audio lives — change it without re-running `mpdc configure` and MPD
stays pointed at the old directory, with no error from either side. Playlists
have no such indirection: `mpd.conf` holds the only copy of that path.

## 3. Changing where the library lives

**Tracks:**

1. Edit `LOCAL_PATH` in `~/dotfiles/.config/rclone-sync-profiles/music-tracks.conf`.
2. `mpdc configure` — re-pick the tracks profile, Enter through the playlists
   prompt to keep the current path; regenerates `mpd.conf`.
3. `mpdc restart` — MPD re-reads config and, with `auto_update "yes"`, rescans.
4. Verify: `mpdc stats`.

**Playlists:** move or re-clone the `music-metadata` repo, then `mpdc configure`
and give the new `playlists/` path. Nothing else records it. Verify with
`mpdc playlists`.

To change anything *other* than the two directories (outputs, replaygain,
buffers), edit `mpd.conf.bak` and then run `mpdc configure` — editing
`mpd.conf` directly works until the next regeneration silently discards it.

## 4. Scheduling: one mechanism only

Timers come from the generic `rclone-sync@` template. The installer reads each
profile's `SCHEDULE` and writes
`/etc/systemd/system/rclone-sync@<profile>.timer.d/override.conf`, then enables
the timer. The profile name is the systemd instance, so
`rclone-sync@music-tracks.service` runs `rclone-sync.sh music-tracks`.

In `asm` → **51**, the `rclone-sync@<profile>.service` entries are hidden while
their timer is enabled: they are `Type=oneshot` and sit inactive between runs, so
showing them beside their timer read as "every sync is stopped". Only the timers
appear. If a sync service *does* show up there, its timer is not enabled.

There is deliberately no second mechanism. Hand-written per-sync units once
existed (`music-playlists.service` and friends, passing the profile name via
`EnvironmentFile` + `MUSIC_SYNC_PROFILE`); they were removed because `%i`
supplies that for free, and running both meant each library synced twice per
interval with two `rclone sync` processes able to overlap on one destination.

Do not reintroduce per-profile unit files. A new sync needs a profile and a
`SCHEDULE`, nothing more.

`music-tracks` is the only music sync left. There was a `music-playlists`
profile on a 3-minute timer until playlists moved to git; it and its drop-ins
were removed by hand, because installation is additive and the tool ships no
uninstall path (see `service-installation.md` §2).

## 5. Keeping playlists out of the music directory

`music-tracks` syncs `Media/Music`, which used to **contain**
`Media/Music/music-metadata/playlists`. That subtree has since been deleted from
Drive and now lives only in the `music-metadata` git repo, so the two excludes on
the profile are **guards rather than filters**:

```sh
RCLONE_OPTS="--exclude=*.m3u --exclude=/music-metadata/**"
```

Keep them. They cost nothing and they are what stops anything that reappears
under `Media/Music` from landing in MPD's `music_directory` — a failure that
shows up as junk in the library rather than as an error. An invariant test pins
both. Playlists are `.m3u` only; there are no `.m3u8` files anywhere in the
remote.

MPD reads playlists solely from `playlist_directory`, which now points into the
git clone and is fed by `git pull`, not by any timer.

> Order matters when adding an exclude for files that already exist locally:
> `rclone sync` does **not** delete excluded files, it orphans them. Propagate
> the deletion first (remove them at the source, let one sync run), then add the
> exclude as a guard. This did not bite during the git migration only because
> the excludes predated it — `music-metadata` was never present locally under
> `music_directory` to be orphaned.

## 6. The MPD daemon

`mpd.service` is a **user** unit that comes from the distro package. It is *not*
installed by `linux-system-manager`, *not* in `$SERVICES_PATH`, and *not* a member
of `personal-services.target` — so it will never appear under `asm` → 51. Manage
it with `mpdc`, which wraps `systemctl --user`:

```bash
mpdc start | stop | restart      # this session
mpdc enable                      # enable + start, persists across reboot
mpdc disable                     # stop + disable
mpdc daemon-status               # systemctl --user status mpd.service
```

Being a user unit, it dies at logout unless **lingering** is enabled
(`loginctl enable-linger <user>` — it is, on this machine). That is the main
reason linger matters here at all.

### It depends on the sync, and nothing enforces that

MPD reads `music_directory` and `playlist_directory` directly off disk.
`music_directory` is populated by the `music-tracks` timer, a **system** unit with
no ordering relationship to the user-scope MPD. On a fresh boot MPD can start
before the first sync completes and index an empty or partial library.

That is not an error state and needs no fix — `auto_update "yes"` means MPD
notices files appearing and rescans. `mpc update` forces it; `mpc stats` shows the
result.

`playlist_directory` is different in a way that works in your favour: MPD reads
stored playlists off disk **on demand**, not from the database. A `git pull` in
the `music-metadata` clone is visible to `mpc lsplaylists` immediately — no
`mpc update`, no restart. Nothing pulls automatically, so playlists are exactly
as fresh as your last pull and no fresher.

Because `playlist_directory` is a git working tree, `mpc save` writes new
playlists straight into the repo as untracked files. That is the intended flow:
save, then commit and push.

### Runtime state lives outside the repo

`~/.local/share/mpd/` holds `mpd.db`, `mpdstate`, `sticker.sql`, `mpd.log` and the
pid file. None of it is version-controlled and none of it should be — the database
is derived from the library, and `mpdc configure` recreates the directory if it is
missing. Deleting `mpd.db` is a safe way to force a full reindex.

### Symptoms

| symptom | cause |
|---|---|
| daemon runs, library empty | sync has not populated `music_directory` yet, or `mpd.conf` points at the old path after a `LOCAL_PATH` change without `mpdc configure` |
| playlists missing | the `music-metadata` clone was never pulled, or `playlist_directory` points somewhere else — check it against the clone, there is no timer to blame |
| MPD refuses to start, complains about `@PLAYLIST_DIR@` | `mpd.conf` was copied from the template without running `mpdc configure` (§2) |
| playlists present but tracks unresolvable | `save_absolute_paths_in_playlists "no"` — entries are relative to `music_directory`, so the two must agree |
| a playlist resolves nowhere on one machine only | CRLF line endings; entries keep a trailing `\r`. The git copies are LF — check `core.autocrlf` before blaming MPD |
| daemon gone after logout | lingering disabled |
| config edits keep vanishing | you edited `mpd.conf` instead of `mpd.conf.bak` (§2) |

## 7. Management commands

| command | alias | does |
|---|---|---|
| `mpd-configurer.sh configure` | `mpdc configure` | regenerate `mpd.conf` from the template + tracks profile + a typed playlists path |
| `mpd-configurer.sh start\|stop\|restart\|enable\|disable\|daemon-status` | `mpdc …` | manage the `mpd.service` **user** daemon |
| `mpd-configurer.sh tracks [term] \| playlists \| playlist <n> \| stats \| status` | `mpdc …` | query the library via `mpc` |
| `mpd-configurer.sh mpc -- <args>` | `mpdc mpc -- …` | raw `mpc` passthrough |
| `rclone-config-manager.sh` | `rclc` | assemble/split the GPG-encrypted rclone backends |
| `music-library-normalizer.py` | `mln` | normalize the on-disk library |
| `mpdtui` | `mtx` / `mt` / `mtp` / `mtt` | full / mini / playlist-search / track-search player |

Sync logs go to the journal under distinct identifiers:

```bash
journalctl -u rclone-sync@music-playlists.service -n 50
```

## 8. Adding a new synced music source

1. Create `~/dotfiles/.config/rclone-sync-profiles/<name>.conf` with the fields
   in §1. Use `DIRECTION="remote-to-local"` unless you intend local edits to
   propagate — `SYNC_TYPE="one"` deletes at the destination.
2. `./do-stow.sh` to link it into `~/.config/`.
3. Set `SCHEDULE`, then `asm` → **55** and pick the new profile; it writes the
   timer drop-in and enables it. `asm` → **54** shows what is already installed.
4. If MPD should use it as the track source, `mpdc configure` and pick it.
5. Attach any hand-written unit to `personal-services.target` — see
   `personal-systemd-services.md`.

Never point a profile's `LOCAL_PATH` at the `music-metadata` clone or anything
inside it. `SYNC_TYPE="one"` deletes at the destination, so such a profile would
not merely duplicate the repo — it would delete the working tree to match the
remote. An invariant test rejects it.

## 9. Retiring a sync

There is no uninstall path, so removal is manual and easy to leave half-done —
a profile deleted from the repo but still enabled means a timer firing forever
against a config file that no longer exists. The full sequence:

```bash
sudo systemctl disable --now rclone-sync@<name>.timer
sudo rm -rf /etc/systemd/system/rclone-sync@<name>.timer.d \
            /etc/systemd/system/rclone-sync@<name>.service.d
sudo systemctl daemon-reload
sudo systemctl reset-failed rclone-sync@<name>.service   # if it ever failed

rm ~/dotfiles/.config/rclone-sync-profiles/<name>.conf
rm ~/.config/rclone-sync-profiles/<name>.conf            # see below
rm -f ~/.config/rclone-sync-profiles/<name>.resync       # bisync marker, if any
```

`systemctl disable` removes the links from both `timers.target.wants` and
`personal-services.target.wants`.

That second `rm` is not redundant. `do-stow.sh` runs plain `stow`, not
`stow -R`, so deleting the source file leaves a **dangling symlink** in
`~/.config/rclone-sync-profiles/`. `mpd-configurer.sh` skips it (its `[[ -e ]]`
test fails on a broken link), but `install.py` globs `*.conf` and will report the
dead profile as missing required fields on every run.
